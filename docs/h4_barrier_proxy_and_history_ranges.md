# H4 barrier panel + history ranges (2026-07-28)

Three related changes to the Beam and Beam2 tabs.

## 1. H4 Barrier — T2 TAX panel, proxied from the x17 DAQ

The barrier position is `XTAX_022_023:POSITION_MEAS` in NXCALS. **We cannot read
it here.** NXCALS is on the CERN Technical Network; banco is on the GPN
(`128.141.21.144/26`) but is *not* TN-trusted, so `cs-ccr-nxcals{5,6,7,8}:19093`
and `acc-py-repo.cern.ch:443` answer `No route to host` (measured 07-26, again
07-28). A LanDB TN-trust request is the open item.

⚠ `ithdp1001.cern.ch:8020` (HDFS) *does* answer from here — it is `10.116.5.218`,
not a TN host, so it is **not** a readiness signal. Only the four `:19093` ports
are. Kerberos is not a blocker either.

The n_TOF x17 DAQ (`ntof-x17-daq.dyndns.cern.ch`) is TN-trusted and already
polls the TAX, writes per-day CSVs and computes the blocked spans. So Flask here
forwards its finished answer rather than standing up a second Spark session
behind a tunnel:

    /sps/tax_state    -> x17 /sps/status  → h4_tax block   (~300 B,  tiles, 5 s)
    /sps/tax_history  -> x17 /sps/tax_history              (~100 kB, trace, 60 s)

Both are in `flask_app/app.py` (`_x17_get`, `X17_BASE`, override with
`X17_FLASK_URL`). On failure they return the panel's existing empty shape, so an
x17 restart blanks that panel only — the rest of the tab is unaffected.

⚠ **Use the DNS name, never the address.** x17 has no static reservation; its
lease is sticky by MAC only and has already moved `.103 → .17` once.

Why not just copy the panel: our `sps_monitor` is an independent re-port whose H4
story is `XBH4.BEND.*` currents + `XBH4.EXPT.*` counters. The barrier has **no
`XBH4.` prefix**, so it never appeared in that survey and there is no TAX code
here to copy the panel onto. The two signals are complementary — BEND currents
say *line powered*, TAX says *barrier across the beam* — and both are kept.

⚠ Do **not** paste x17's SPS import block (`H4_TAX_VAR`, `tax_blocked_intervals`,
…) into `app.py`: those symbols do not exist in our controller and the
`ImportError` at module scope takes the **whole** Flask app down. The proxy
imports nothing new, which is the point.

The spans are **access candidates**, not confirmed accesses: position says the
line is blocked, not why. Confirm against the H4 flux counters — see
`docs/H4_ACCESS_INFERENCE.md` in the x17 repo.

## 2. `files[-2:]` capped every history request at ~2 days

`/beam/history` and `/sps/history` both did `pd.concat(... files[-2:])`, loading
at most two per-day CSVs however large `hours` was. A 336 h request returned only
the last two days — which reads exactly like an archive that stops there, not
like a bug. Both now size the window from the request:

    keep = max(2, int(hours // 24) + 2)

(the logic `/sps/tax_history` on x17 always had). The Beam Intensity Trend and
Per-cycle Trend panels gained 6 h / 24 h / 3 d / 7 d / 14 d pickers
(`#beam-range`, `#sps-range`); the default is still 6 h.

⚠ If a plot here ever looks like it "has no older data", suspect a file-window
cap before believing the archive.

At 14 d with `max_points=3000` the series is decimated to ~5 min/point — good for
spotting beam-off periods and access cadence, not for per-cycle detail.

## 3. History backfilled to 2026-07-14

`beam_intensity_*.csv` and `sps_spill_*.csv` now start 07-14 (were 07-22);
x17's `h4_tax_*.csv` likewise, which this tab sees through the proxy.

Generated by running **our** `sps_monitor/backfill_nxcals.py` **on the x17 box**
(the only machine that can reach NXCALS) with `SPS_BEAM_LOG_DIR` /
`SPS_SPILL_LOG_DIR` pointed at a scratch dir, then copying the CSVs into
`beam_monitor/logs/`. ~90 s/day.

⚠ It must be **our** controllers, not x17's: our `sps_spill` schema is 17 columns
(9 base + 8 `h4_bend_*` / `h4_gif_*` / `h4_hna162_005`), x17's own is 9.
Generating with theirs silently drops the H4 columns `/sps/history` reads. Check
the header matches before copying anything in.

`sps_monitor/backfill_tax_nxcals.py` is here for parity and for running from
lxplus (it falls back to defining the TAX constants itself, since our controller
has none). It cannot run on banco — no NXCALS.
